Wrap vs alone — fixed order, or an entry-declared choice? Fixed (wrap wins) is simpler; a tag is more explicit and avoids the case where a payload implements both and you wanted "alone".

Do payload-only entries become first-class? Currently .task is mandatory. If yes, to_task gets a requires { e.task; } guard, and the queue concepts get a note that not every entry carries a task. Non-trivial.

payload() by value or reference? Currently by value. to_task moves out of the local copy, so move-only payloads work, but every payload is copied once at pop even when the caller only wanted .task. If a payload is expensive and the wrap form isn't taken, that's waste. A payload() && overload (rvalue-only) would make that cost explicit.

Does the scheduler's inherited_payload inheritance make sense for a behaviour payload? The state stashes a copy for downstream coroutines. If the payload is a std::function<void(Task)>, inheriting it copies the closure. Probably fine; worth being aware of.

Should Loop get the same treatment? It stores shared_ptr<Task> because entries persist across iterations. Payload-per-iteration would require a different internal layout.
